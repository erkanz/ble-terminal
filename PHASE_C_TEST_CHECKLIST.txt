1. MONITOR OPEN / BASIC CAPTURE
-------------------------------
1) Start BLESerialTerminal.exe.
2) Connect RT-950 using Auto Detect.
3) Confirm main terminal reaches RADTEL KISS READY.
4) Open View -> BLE Notification Monitor...
5) Receive or generate BLE/KISS traffic.

Expected:
[ ] monitor opens without changing BLE connection state
[ ] each FFE1 BLE notification produces one monitor row
[ ] row sequence numbers increase monotonically
[ ] Time is populated
[ ] Device is populated
[ ] Service shows FFE0 for RT-950 data traffic
[ ] Characteristic shows FFE1
[ ] Source shows Auto Detect/main source metadata
[ ] Mode reports Notify/Indicate appropriately
[ ] Len matches notification byte length
[ ] HEX is visible in selected-row detail
[ ] ASCII-safe view is visible
[ ] terminal RAW BLE NOTIFICATION logging continues normally
[ ] Phase B KISS/AX.25/APRS decoding continues normally


2. FRAGMENTED KISS RELATION
---------------------------
Use a normal APRS packet that arrives as several BLE notifications.

Expected:
[ ] monitor shows the individual BLE notification fragments separately
[ ] KISS column does not falsely turn each fragment into a complete frame
[ ] KISS count becomes non-zero only when a fragment completes one or more KISS frames
[ ] monitor KISS tracking does not change main terminal KISS reassembly
[ ] decoded packet window still receives exactly the main decoded packet(s)


3. PAUSE / RESUME DISPLAY
-------------------------
1) With traffic active, click Pause display.
2) Generate several notifications while paused.
3) Observe counters.
4) Click Resume display.

Expected:
[ ] state reads PAUSED (capture continues)
[ ] visible rows stop advancing while paused
[ ] captured notification counter continues increasing
[ ] captured byte counter continues increasing
[ ] main terminal RX remains live while monitor display is paused
[ ] Resume repopulates the visible list with captured backlog
[ ] no BLE reconnect is required

IMPORTANT
Pause is display-only. If counters stop increasing while traffic is known to arrive,
that is a FAIL.


4. CLEAR / BOUNDED HISTORY
--------------------------
[ ] Clear removes monitor history
[ ] Clear resets monitor notification/byte/per-characteristic counters
[ ] Clear does NOT clear the main terminal log
[ ] Clear does NOT clear the Phase B decoded-packet history
[ ] capture resumes on the next incoming notification
[ ] sequence numbering remains monotonic after Clear
[ ] sustained capture remains responsive

Automated coverage already proves a synthetic 20,000-notification input is counted while
history remains bounded. Hardware test only needs to verify normal live behavior.


5. COPY / EXPORT
----------------
Select a notification row.

[ ] Copy HEX places the row HEX on the clipboard
[ ] Copy text places the ASCII-safe form on the clipboard
[ ] Export creates TSV output
[ ] export contains sequence/timestamp/device/service/characteristic/source/mode/length
[ ] export contains HEX and ASCII-safe data
[ ] export includes related KISS-frame count when available
[ ] export does not interrupt live capture


6. GATT INSPECTOR MULTI-CHARACTERISTIC CAPTURE
----------------------------------------------
1) Keep Notification Monitor open.
2) Open GATT Inspector.
3) Enable Notify or Indicate on another notification-capable characteristic if the
   connected device exposes one (for RT-950 this may be FF31/FF32 depending on firmware).
4) Generate traffic for that characteristic if possible.

Expected:
[ ] monitor shows characteristic-specific rows separately
[ ] Service UUID is correct
[ ] characteristic UUID is correct
[ ] Source/reused metadata is shown
[ ] per-characteristic counters update independently
[ ] no additional CCCD write is performed merely because Notification Monitor is open
[ ] monitor follows Inspector's existing active subscription instead of creating a competing one
[ ] disabling the Inspector subscription stops new monitor rows for that characteristic

If no second notification-capable characteristic can be exercised on the available
hardware, mark those specific items NOT AVAILABLE rather than fabricating PASS.


7. RT-950 FFE1 DUPLICATE PROTECTION
-----------------------------------
The main Auto Detect FFE1 characteristic is already captured by the main terminal monitor
observer. GATT Inspector may reuse the same cached FFE1 object/CCCD.

Test:
1) Connect RT-950 and open Notification Monitor.
2) Receive traffic and note FFE1 row count.
3) Open GATT Inspector while the same Auto Detect FFE1 subscription is active.
4) Receive equivalent traffic again.

Expected:
[ ] Inspector reports cached/reused FFE1 as before
[ ] main FFE1 CCCD remains active
[ ] opening Inspector does not intentionally double the monitor FFE1 rows
[ ] terminal receives each notification normally
[ ] KISS/APRS decode is not duplicated
[ ] closing Inspector does not stop later monitor or terminal FFE1 RX


8. DISCONNECT / RECONNECT
-------------------------
[ ] disconnect removes/invalidates the connection-scoped capture observer safely
[ ] no exception appears when a disconnect races an incoming notification
[ ] reconnect attaches capture to the new connection characteristic wrapper
[ ] notifications after reconnect appear in the monitor
[ ] old/stale GATT wrapper is not reused
[ ] main terminal Auto Reconnect behavior remains unchanged
