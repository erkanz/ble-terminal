======================================================================
1. PROJECT OBJECTIVE
======================================================================

Build a production-ready Windows BLE/GATT application that remains useful as:
1) a generic BLE-UART serial terminal,
2) a low-level GATT inspection/debug tool,
3) a KISS / AX.25 / APRS protocol analyzer,
4) a structured session-capture/replay system,
5) a GATT snapshot/device-comparison tool,
6) a local KISS TCP bridge,
7) eventually a multi-device diagnostic environment.

Reliability priorities:
- preserve working BLE behavior while adding features
- observability before abstraction
- retain raw evidence when higher-level decode fails
- correct connection-scoped GATT ownership/disposal
- deterministic tests where possible
- bounded UI/log histories
- never present UI-only fake functionality
- do not rewrite stable BLE connection code merely for style
- never infer RF success from a successful GATT write

5. NON-NEGOTIABLE BLE/GATT BASELINE
======================================================================

GENERIC BLE-UART
- Auto Detect remains supported
- Nordic UART Service remains supported
- HM-10 FFE0/FFE1 remains supported
- generic UART-style GATT remains supported
- manual Custom UUID mode remains supported

RT-950 PRO BASELINE
Expected profile:
- service FFE0
- write FFE1
- notify FFE1
- same characteristic may be RX and TX
- profile RADTEL_RT950_KISS only when device/signature logic matches
- HM-10 must not be called RT-950 merely because FFE0/FFE1 exists

Expected readiness chain:
    FFE1 FOUND
    -> FFE1 VALUECHANGED HANDLER ATTACHED
    -> FFE1 CCCD WRITE RESULT=Success
    -> FFE1 NOTIFY ACTIVE
    -> RADTEL KISS READY
    -> RAW BLE NOTIFICATION

GATT CACHE / OWNERSHIP
- Auto Detect retains selected GattDeviceService
- retains write and notify characteristics
- retains complete characteristic list for selected service
- cached wrappers are connection-scoped only
- reconnect creates fresh wrappers
- Inspector reuses cached Auto Detect FFE0 objects when applicable
- Inspector must not issue second cached FFE0 GetCharacteristicsAsync merely to redraw tree
- Inspector must not dispose Auto Detect-owned live objects
- duplicate non-owned wrappers may be disposed safely

CCCD / NOTIFY
- attach ValueChanged before CCCD enable
- avoid duplicate handler attachment
- use result-bearing CCCD API
- log real communication/protocol status
- only Success marks notify active
- if RT-950 CCCD fails, keep connection available for Inspector diagnostics
- active cached FFE1 subscription should be reused rather than blindly rewritten

GATT SERIALIZATION
- main terminal and Inspector share one GATT operation gate
- discovery/read/write/CCCD operations do not race independently
- notification callbacks must not be blocked by that gate
- manual command queue must not merge queued payloads

RAW / KISS
- raw notification evidence precedes protocol parsing
- source characteristic, byte count and HEX remain observable
- fragmented BLE notifications preserve KISS stream state
- repeated FEND and FESC/TFEND/TFESC remain supported
- malformed/non-KISS bytes remain visible

GATT INSPECTOR
Must preserve:
- services/characteristics/descriptors
- short + normalized UUIDs
- property flags
- manual Read/Write
- Notify/Indicate enable/disable
- multiple notification-capable characteristics
- CCCD result logging
- source/reused/ownership metadata
- cached FFE0/FFE1 reuse

TERMINAL/UI BASELINE
- full dark mode + dark scrollbars
- configurable terminal foreground/background
- File / View / Settings / About menus
- Export Log
- LF default
- Local echo default OFF
- Enter-to-send
- transparent multi-resolution icon
- decoded AX.25/APRS details available in dedicated window, not injected into serial output

6. DIAGNOSTIC / PROTOCOL PRINCIPLES
======================================================================

Layering is additive:
    RAW BLE -> KISS -> AX.25 -> APRS

A higher-layer failure must not remove lower-layer evidence.

Diagnostics should distinguish:
- connection lifecycle
- service/characteristic discovery
- descriptor/CCCD operations
- Auto Detect decisions
- cached vs fresh/reused objects
- GATT status / protocol error / HRESULT when available
- raw notifications
- raw writes
- KISS frame boundaries
- AX.25/APRS decode results
- TX operations
- disconnect/reconnect cleanup

Prefer shared event observation over competing BLE subscriptions.
Notification monitoring, structured logging, capture/replay and protocol parsing should observe same connection data without owning duplicate CCCD subscriptions.

Windows GATT write result semantics:
- WRITE START RESULT=ACCEPTED means WinRT accepted creation/submission of the async GATT operation
- WRITE COMPLETE reports real GattWriteResult status / numeric status / protocol error when available
- WRITE SUBMITTED NO_RESPONSE means the characteristic write type intentionally does not require ATT response
- none of these messages proves RF transmission or OEM command acceptance
