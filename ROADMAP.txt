======================================================================
1. PROJECT OBJECTIVE
======================================================================

Build a production-ready native Windows BLE/GATT terminal and diagnostic application.
It must remain useful both as:
1) a generic BLE-UART terminal,
2) a low-level GATT inspection/debug tool,
3) a KISS / AX.25 / APRS protocol analyzer,
4) a session-capture and device-comparison tool,
5) a KISS TCP bridge for external applications.

This is not intended to be a toy/demo application.
Changes must favor reliability, observability, recoverability, protocol correctness,
clean resource ownership, and useful diagnostics.

The project must preserve existing working BLE behavior while features are added.
Do not rewrite stable BLE connection code merely for style/refactoring.

4. NON-NEGOTIABLE EXISTING BASELINE
======================================================================

The following are existing required behaviors and must not regress.

GENERIC BLE-UART
- Auto Detect BLE-UART remains supported.
- Nordic UART Service (NUS) remains supported.
- HM-10 style FFE0/FFE1 remains supported.
- generic UART-style GATT profiles remain supported.
- manual Custom UUID mode remains supported.

RT-950 PRO
Expected device/profile behavior:
- typical device name: walkie-talkie / RT950 / RT-950 / RADTEL-family identification
- service: FFE0
- write characteristic: FFE1
- notify characteristic: FFE1
- same characteristic may be RX and TX
- profile label: RADTEL_RT950_KISS when RT-950 identity/signature matches
- genuine HM-10 devices must not be mislabeled as RT-950 only because FFE0/FFE1 exists

Expected RT-950 readiness chain:
    FFE1 FOUND
    -> FFE1 VALUECHANGED HANDLER ATTACHED
    -> FFE1 CCCD WRITE RESULT=Success
    -> FFE1 NOTIFY ACTIVE
    -> RADTEL KISS READY
    -> RAW BLE NOTIFICATION

GATT CACHE / OWNERSHIP
- Auto Detect retains the selected GattDeviceService.
- Auto Detect retains selected write characteristic.
- Auto Detect retains selected notify characteristic.
- Auto Detect retains the complete characteristic list discovered for selected service.
- cached GATT wrappers are connection-scoped only.
- never reuse stale wrappers after disconnect/reconnect.
- FFE0/FFE1 shared RX/TX characteristic is supported.
- GATT Inspector must reuse cached Auto Detect FFE0 data when service UUID matches.
- Inspector must not perform a second GetCharacteristicsAsync on cached FFE0 merely to redraw the tree.
- false "FFE1 present: NO" after AccessDenied/partial rediscovery must not return.
- duplicate service wrappers may be disposed.
- Auto Detect-owned live service/characteristic objects must not be disposed by Inspector.

CCCD / NOTIFICATION STATE
- attach ValueChanged before CCCD enable.
- avoid duplicate handler attachment.
- use a result-bearing CCCD write API.
- log real status, status code, and ATT protocol error when available.
- only Success marks notify/CCCD as active.
- if RT-950 CCCD enable fails, keep BLE connection alive for Inspector diagnostics.
- if Inspector enables cached FFE1 after main CCCD failure and succeeds,
  main RT-950 state should become READY.
- if main CCCD is already active, Inspector should not blindly write CCCD a second time.

RAW RX / KISS
- raw BLE notification must be observable before KISS parsing.
- log source characteristic UUID.
- include byte length and HEX.
- KISS decoder state must survive BLE notification fragmentation.
- BLE notifications may arrive in small fragments such as 20-byte chunks.
- FEND/FESC/TFEND/TFESC unescaping must remain supported.
- malformed/non-KISS data must still be visible in raw notification logging.

GATT OPERATION SERIALIZATION
- main terminal and Inspector share one GATT operation gate.
- discovery/read/write/CCCD operations must not race independently.
- notification callbacks must not be blocked through that operation gate.
- do not reintroduce avoidable GATT_BUSY-style concurrency.

GATT INSPECTOR
Must preserve:
- discovery of services
- characteristics
- descriptors
- short + normalized UUID display
- characteristic property flags
- manual Read
- manual Write
- Notify / Indicate enable/disable
- multiple notification-capable characteristics
- source UUID logging
- CCCD status/result logging
- ownership/source/reuse metadata
- cached FFE0/FFE1 reuse for RT-950

UI / TERMINAL BASELINE
- full dark mode
- dark scrollbars
- configurable terminal foreground/background colors
- File / View / About menus
- Export Log
- LF default line ending
- local echo default OFF
- Enter-to-send
- transparent multi-resolution application icon

Do not regress these defaults while adding phases.

5. LOGGING / DIAGNOSTIC PRINCIPLES
======================================================================

Logging must make it possible to distinguish:
- device connection lifecycle
- service discovery
- characteristic discovery
- descriptor/CCCD operations
- Auto Detect profile decisions
- cached vs freshly discovered objects
- source/reused/ownership metadata
- GATT status values
- HRESULT when available
- raw notifications
- KISS frame boundaries
- protocol decode results
- TX operations
- disconnect/reconnect cleanup

Do not hide malformed or unexpected data.
Raw evidence must remain available even if higher-level parsing fails.

Protocol parsing must be additive:
RAW BLE -> KISS -> AX.25 -> APRS
A failure at a higher layer must not remove lower-layer data from logs/monitoring.

Prefer one central processing pipeline for incoming notification data so that:
- raw logging,
- KISS reassembly,
- AX.25 decode,
- APRS decode,
- session capture,
- monitoring,
can observe the same event without competing BLE subscriptions.

STATUS: NOT STARTED
PRIORITY: HIGH
----------------------------------------------------------------------

Purpose:
Convert the terminal from raw KISS visibility into a real layered protocol analyzer.

Architecture rule:
Parsing pipeline must remain:
    raw BLE notification
    -> per-characteristic KISS stream reassembly
    -> KISS frame decode
    -> AX.25 decode
    -> APRS decode

Lower layers must remain visible even if upper-layer parse fails.

B1 - KISS FRAME MODEL
Implement a structured KISS frame representation:
- source device
- source characteristic UUID
- timestamp
- raw frame bytes
- unescaped bytes
- KISS port
- KISS command
- payload length
- malformed/error flags

Handle:
- FEND boundaries
- repeated FEND
- FESC / TFEND / TFESC
- fragmented notifications
- multiple frames inside one BLE notification
- malformed escape sequences without losing raw evidence

B2 - AX.25 DECODER
Decode at minimum:
- destination callsign + SSID
- source callsign + SSID
- digipeater/path list
- H/repeated bit where meaningful
- control field
- PID
- information field
- frame type where determinable

Important:
KISS-delivered TNC frames may not contain an HDLC FCS.
Do not reject normal KISS payload solely because no FCS is present.

B3 - APRS DECODER
Decode/display useful APRS data without hiding original packet text.

Target categories:
- position reports
- timestamped position
- APRS message
- ACK/REJ
- status
- object
- item
- telemetry
- weather fields where present
- Mic-E where practical
- third-party encapsulation where practical
- unknown/unsupported type shown safely as raw APRS info

For every decoded packet show:
- source
- destination
- path
- APRS type/category
- original information field
- parsed fields
- parse warnings

B4 - UI
Add a dedicated decoded-packet view or inspector without removing terminal/raw views.

Required usability:
- timestamp
- source
- destination
- path
- type
- summary
- raw HEX access
- raw text access
- copy/export

B5 - TESTS
Create protocol fixtures for:
- complete frame in one notification
- fragmented KISS frame
- two KISS frames in one notification
- escaped FEND/FESC
- malformed escape
- standard APRS position
- APRS message + ack
- object/item
- unsupported APRS type
- KISS payload without FCS
